## 1. 产品定位

面向独立经营单家小型民宿的老板或店长，帮助他们减少重复沟通和事务处理时间，并把经营数据与周边线索转化为容易理解、可由自己决定的下一步。产品的核心是 **AI 辅助经营与任务自动化**：常见咨询可由 AI 依据民宿资料即时回复；涉及承诺、资金或现场安排的例外事项交还经营者决策。分析和探索为这些工作提供依据，而不是彼此孤立的三个助手。

当前痛点仍是待验证的产品假设：经营者一人兼顾接待、订单、数据和推广；客人需要及时回复；数据虽多却难以形成行动；内容创作又占用时间。后续应通过真实经营者访谈和任务观察验证。

## 2. 目标用户与核心任务

- **主要用户：** 日常亲自接待和管理、时间紧张的小型民宿经营者。初期按单店场景设计。
- **用户想完成的事：** 快速处理客人消息与异常订单；一眼看懂入住、预订、价格、需求和满意度；借周边信息形成合适的推广草稿；维护 AI 回复所依据的真实民宿资料。
- **成功体验：** 打开首页知道今天要看什么；在工作页区分“AI 已处理”和“待我决定”；查看建议时能追溯依据；需要对外承诺或改变订单时由经营者确认。

## 4. 核心用户旅程

### 4.1 常见咨询：资料 → AI 回复 → 经营者接手

1. 经营者在 Mine 维护早餐、入住、交通合作服务等事实资料，选择是否开启 AI 随时回复。
2. 客人发来咨询；系统识别意图，检索相关资料，生成有依据的回复。资料不足、需第三方确认或可能形成承诺时，不自行编造确定答案。
3. Work 的消息列表显示客人、最近回复及“AI 已回复”状态；经营者进入对话，可查看原问题、AI 回复和依据，再补充自己的回复。
4. 经营者获得及时响应与接手能力；系统保留回复及人工补充的状态记录。

原型用早餐时间和机场接送推荐两段固定示例演示此旅程。真实消息接入、资料检索、模型生成和实际发送属于后续开发，不能把演示文本称为实时 AI 回复。

在真实认证与数据库尚未接入时，可增加一条**独立的本地演示链**：经营者在 Work 输入新问题，服务端读取 Mine「回复依据」保存到本机的已确认事实调用规则判断接口，返回可编辑前的草稿、引用依据或转人工原因。界面明确显示“规则演示、未发送”；此链读取专用的 SQLite 本机资料，不读取其他 Mine 示例会话值、不连接真实客人，也不替代正式功能的权限验收。

### 4.2 例外事务：识别 → 建议 → 人工决策 → 记录

客人提出提前入住或退款申请时，系统整理订单、已存规则与缺失信息，给出处理方案。经营者在 Work 查看依据并选择确认或暂缓；结果进入完成记录，首页待办同步更新。未来若接入预订和支付系统，外部操作与通知需要明确权限、状态回执和失败处理。当前原型的决定只改变会话内演示状态，不会取消真实订单、退款或通知客人。

无真实订单平台期间，独立的规则演示只读取固定示例订单：提前入住缺少清洁确认时先建议核实，不直接允许；示例退款可按日期和已付金额计算建议额，但经营者的按钮只保存**拟采取的决定**。已完成记录必须标明“未执行外部操作”，不能把方案保存写成退款完成或通知已发送。

### 4.3 经营决策：并列指标 → 单项详情 → 总结 → 行动

经营者在 Analysis 同时看到自身预订指标和市场/客人参考指标；点击一张卡片，下方只呈现该指标的详情，不重复铺满全部图表。入住率可切换 7/28 天并查看每日数值；其他详情涵盖预订进度、房价位置、需求指数和评分/评价话题。页面末尾用易读文字总结现状，再给出可执行的下一步，分别通往 Explore 的推广与周边比较，或回到满意度反馈。市场需求与自身入住率必须清楚区分。

### 4.4 发现机会：周边线索 → 推广草稿

经营者在 Explore 选择日期，查看需求强弱及示例活动；再参考自身工作日空房、客人评价和附近住宿。选择活动或服务后，系统组合已确认的信息，生成所选渠道的文案草稿（原型示例包括小红书帖子）；经营者可编辑并保存，发布前应核实活动、房价和可订日期。生成内容不自动发布，也不自动修改房价。

## 5. MVP 功能范围

| 优先级 | 能力 | 最小可用要求 |
| --- | --- | --- |
| P0 | 民宿资料与回复依据 | 可维护关键事实；回复明确指出依据；资料缺失时提示人工处理。 |
| P0 | 消息与 AI 协助 | 有客人消息列表和对话；常见问题可生成/发送有依据的回复；经营者可查看、补充或接管；开关状态清楚。 |
| P0 | 例外事务决策 | 提前入住、取消退款等需要承诺或资金处理的事项进入待决策；展示规则、缺失信息、可选动作和结果状态。 |
| P1 | 经营分析 | 五类指标同屏概览，选中后查看对应详情；可读的经营总结与行动入口；指标口径和数据时间清楚。 |
| P1 | 市场探索与内容草稿 | 日期需求、周边线索、价格比较；基于可核实信息生成、编辑并保存推广草稿。 |
| P1 | 首页串联 | 日程、经营重点和待决策项能导航到对应工作，处理状态一致。 |

第一条可交付的完整功能链建议选 **“客人常见咨询的 AI 协助与人工接手”**，因为它直接体现节省时间的主价值。登录和页面外壳仅是进入功能的基础设施，不单独算核心功能。随后扩展例外事务和分析/推广闭环。

## 6. 当前原型与正式 MVP 的区别

`frontend/` 已实现五页可点击原型和上述主要交互形态，数据、客人、评价、活动和回复均为虚构示例。部分语言、资料、决策和草稿保存在浏览器本次会话中。另有独立的 `/login` 与受保护 `/app` 占位入口；登录代码和后端令牌/民宿权限校验已经过本地模拟测试，但尚无 Supabase 项目，不能声称真实账号已打通。Work 的新咨询及例外事务演示已能经 Next.js 入口调用 FastAPI 规则接口，返回只读草稿或建议；新咨询已使用本机持久化事实，例外事务订单仍为固定示例。已接入可选模型推理（虚构测试），没有正式多用户数据库、预订/支付/OTA 接口、消息发送、文件解析或公开发布。历史示例对话中的“AI 已回复”等均是**情景演示**；真实 MVP 必须以实际处理结果和回执更新状态。

在接入真实服务之前，每一处示例数据、推断及外部操作应保持清楚标记，不能用模拟成功代替真实成功。真实接入的数据来源、使用权限、隐私方案与指标口径仍待确认。

## 7. 非目标与硬边界

- 初期不做完整 PMS、财务结算、多店管理或跨 OTA 的全量库存同步。
- 不依据虚构市场信号声称实时预测，不展示无法核实的真实房源、评价或活动。
- 未经权限、规则核对和操作回执，不自动执行真实退款、改价、订单变更或对外发布。未来可按明确政策逐步自动化低风险任务，例外保留人工接管。
- 不让 AI 对入住时间、接送可用性、优惠、退款金额等做缺乏依据的确定承诺。
- 不为提高功能数量而重复分区：评价洞察归 Analysis；内容推广归 Explore；消息和需要经营者决策的事务归 Work。

## 8. 验收标准

1. **主流程可走通：** 从首页进入 Work，对一条客人咨询查看 AI 回复和依据、补充人工回复；开关停用时新的自动回复不发生。真实 MVP 还需验证发送结果，演示版只验证 UI 状态。
2. **例外可控：** 提前入住和退款展示事实、规则及风险；经营者能选择处理方案；待办与完成记录同步；若真实外部操作失败，不得显示为完成。
3. **分析清楚：** 五项指标同时可见，点击任一指标只展开相应详情；日期/周期、单位、数据来源和“需求≠入住率”可理解；总结以文字给出重点而非堆砌数字。
4. **探索可行动：** 日期选择影响对应需求说明；周边线索可进入推广流程；草稿可编辑和保存，发布前需要核实，且无自动发布或自动调价。
5. **资料可信：** 修改关键民宿资料后后续回复使用新值；上传资料不会绕过审核直接改写事实。
6. **状态完整：** 主流、加载中、无数据、资料不足、外部接口失败都有明确反馈和可恢复路径；中英文切换与移动端主要交互可用。

## 9. 待验证决策

真实经营者最耗时的咨询类型；哪些问题可安全自动回复；平台消息和订单数据的可用性；需求指数的合法来源与口径；推广渠道的发布流程；经营者可接受的自动化授权范围。确认后应更新本 PRD，再调整开发范围。
