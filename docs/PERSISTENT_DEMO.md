# 云端演示账号准备

更新：2026-10-24。用户已授权将演示数据迁到独立云端账号；当前账号尚未创建，下面不是已完成的上线记录。

## 账号与隔离

在现有Supabase项目的Authentication → Users中创建 `demo@example.invalid`，密码 `staycraft-demo`，并自动确认邮箱。这是明确公开的演示凭据，账号内只能放虚构资料。不要修改已有账号，不把真实订单、联系方式或密钥放入演示民宿。

使用正常Auth与RLS，一账号一民宿，登录入口仍为正式 `/login`。持久化演示不依赖3106内存夹具，也不能通过开启托管测试开关实现。当前Edge管理页连接持续超时，需要用户先完成Auth账号创建；不要直接用业务SQL构造真实Auth登录凭据。

## 数据准备与导入

从仓库根目录运行 `node frontend/scripts/prepare-persistent-demo.cjs`，生成被Git忽略的 `frontend/qa-persistent-demo-seed.sql`。脚本只生成SQL，不联网、不执行数据库写入、不创建Auth账号。

导入前审查SQL，再通过已授权管理连接执行。它只寻找已确认的指定演示邮箱，事务内锁定并检查该民宿为空；发现资料、房型、客房、订单或会话即停止，禁止覆盖或自动重置。没有Auth账号时失败，不影响其他民宿。

包含虚构民宿资料、独立公开须知、3种房型、6间客房、14笔订单（9笔已完成）、1条咨询。日期以实际导入当天的北京时间生成；保存后不会随访问重写历史。房型图片未批量导入，后续通过演示账号正常上传。自动回复不随导入开启，可登录后按需开启和验证。

## 验证与保留

`node frontend/scripts/prepare-persistent-demo.cjs --test` 生成独立的事务回滚测试SQL，使用临时虚构Auth行，只能用于测试，不创建可登录账号。已验证数据计数、再次导入拒绝且已有数据不变、其他账号不可读演示客房；测试写入全部回滚。

真正导入后仍须核对：正常登录/刷新持久化、当前账号看不到演示数据、示例入住/退房/清洁/取消与收入分析、客人资料/预订/消息同步。后台重启不清空云端数据，明确人工确认前不做清理或重新初始化。现有3106继续作为本机隔离样本，和云端账号是两个不同入口。
