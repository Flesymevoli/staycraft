# 数据库结构现状与下一轮讨论

版本：2026-10-22。本文记录已实施的云端结构；模型对正式数据的调用保持关闭。

## 最新确认：一个账号对应一家民宿

账号是最高层。每个登录账号默认拥有一家民宿，登录后直接进入自己的工作台，不选择加入哪家民宿，也不需要多民宿切换。建议在民宿表保存唯一的owner_user_id，关联Supabase Auth账号；房型、客房、订单等沿民宿归属隔离。

已完成single_account_property迁移：properties.owner_user_id非空且唯一，页面/API按账号所有权鉴权；首次访问自动建立空民宿。原membership表保留为历史记录，客户端权限已撤销，不再作为业务鉴权来源。原民宿、房间、订单ID及图片引用保持不变。

可阅读的虚构示例见[DATABASE_EXAMPLES.md](DATABASE_EXAMPLES.md)，它是结构讨论用的表格，不是云端真实数据或可直接导入的迁移。

## 当前云端实际存在的表

| 表 | 对应业务 | 当前内容 |
| --- | --- | --- |
| properties | 账号拥有的唯一民宿 | 民宿ID、唯一owner_user_id、名称、建立时间、库存并发版本inventory_revision |
| property_memberships | 旧版关联历史，不再参与业务 | 保留旧行供追溯，客户端已无访问权限 |
| property_details | 民宿基本资料 | 名称、地址、早餐和入住时间、须知等JSON，以及防覆盖的revision |
| room_types | 可复用房型 | 民宿ID、稳定房型ID、名称、床型、容量、基础价格、图片路径 |
| rooms | 具体客房 | 民宿ID、稳定客房ID、房号、楼层、所属房型ID、清洁和启停状态 |
| property_inventory | 拆表前的只读迁移快照 | 保留旧JSON供追溯，不再写入，也不作为当前库存来源 |
| direct_bookings | 直接预订订单 | 民宿、房间/房型ID、当时名称/房号/价格快照、日期、客人姓名和电话、预计到店、订单状态、取消申请和请求去重信息 |
| conversations | 站内会话 | 民宿、会话ID、浏览器能力令牌摘要、客人显示名与更新时间；不向经营端暴露令牌摘要 |
| messages | 站内消息 | 民宿、会话、发送者guest/owner、正文、时间、去重请求号及回复目标；不保存AI草稿为已发送消息 |
| reply_drafts | 回复草稿与依据记录 | 会话、最新客人消息、原问题快照、资料版本、语言、生成模式、决定/引用和时间；始终待审核、未发送 |

用户登录由Supabase Auth的auth.users负责；图片文件放room-photos存储桶，数据库保存路径。房型和客房已拆为实际物理表，可在Table Editor中查看。

rooms通过(民宿ID,房型ID)引用room_types；订单通过复合外键引用同民宿的客房和房型，不能跨账号串房。订单保留成交时的名称、房号和价格快照；经营端订单和日程显示当前客房房号，改房号不会丢失原订单关联，也不改变历史金额。

前端仍接收types/rooms结构，由get_room_inventory从新表组合；save_room_inventory校验账号归属、旧版本和完整配置，在事务内保存并更新inventory_revision。预订分房、取消与配置保存锁定同一民宿行，避免房量分配与编辑互相穿透。客户端只有新表的本人读取权限，不能绕过保存接口直接改表；已有客房保留并通过停用处理，不直接删除。

本机SQLite另存示例事实、会话、消息、AI草稿、事务方案和指标样本，与新云端会话分开。站内回复草稿现已接云端记录；真实模型调用默认关闭，当前使用资料规则建议。

reply_drafts按民宿/会话/消息/资料版本/语言/模式去重。草稿生成只读取已保存的早餐和常规入住时间，问题从数据库最新客人消息取得；不能通过浏览器传入假事实。保存时重新核对最新消息与资料版本，引用必须精确匹配当前资料，禁止将草稿写成sent=true。相同依据复用已有结果，但仍重新核验上下文；准备草稿不会插入messages。每次人工发送继续走原消息回执流程。

站内会话按(民宿,客人会话摘要)唯一。客人沿用直订HttpOnly Cookie，仅通过能力接口读写自己的消息；经营端按owner RLS读取，通过reply_conversation回复，不能直接改写旧消息。首次创建和留言限额在事务内校验：单民宿最多500会话，单会话最多100条客人消息，每分钟最多10条客人消息。每条客人消息最多对应一条经营端回复，回复前必须核对当前最新消息；请求重试返回原记录。消息回执表示已进入本站会话，不表示OTA发送或客人已读。列表显示最近50条会话，详情最多200条消息。

## 建议讨论的目标结构

1. **账号、民宿、基本资料**：一个账号默认拥有一家民宿，以唯一owner_user_id关联；MVP不需要成员关联、加入民宿或多民宿切换。正式业务沿民宿归属隔离。
2. **房型**：单独一张表，保存可复用的图片、床型、容量和基础价格。
3. **具体客房**：单独一张表，保存实际房号、楼层、房型引用、清洁和启用状态。
4. **订单**：引用具体客房和房型，保留成交时的价格/名称快照与客人必要信息。暂时不强加独立客人账号或支付表。
5. **会话与消息**：分别保存咨询归属和逐条消息；发送者、草稿、已发送/失败必须区分。
6. **AI处理记录与待审核事务**：记录输入引用、输出、处理状态、经营者选择；不能用AI生成结果替代已执行操作。

账号、房型、客房、订单、站内会话/消息及草稿处理记录已实施；实际退款等待审核事务仍需后续开发。

## 要先统一的规则

- 清洁状态是已清洁/待清洁；预订状态是已确认/已取消；实际入住状态不能由这两项直接推断。正式入住/退房尚未接通。
- 没有真实收付款，就不新增假付款或假退款记录。
- 入住日含、离店日不含；订单快照与当前房型价格分开保存。
- 首页、工作台、日程、分析读取同一套订单，不分别维护五份数据。
- 课程演示样本与正式民宿数据分开。可重置示例，不重置真实用户资料。
- 拆房型/客房表时保留稳定ID、旧图片及订单引用；先备份、增量迁移、验收后切换读取，不推倒重来。

## 正式订单预订指标（2026-10-22）

get_booking_metrics(property, days) 是仅认证owner可执行的只读RPC，保留现有RLS；days仅允许7/28。以服务器北京时间今日起算，统计区间含今日、离店日不计。只统计confirmed订单，取消待审核仍占预订，cancelled排除；同一房间同一天去重。

启用库存间夜=当前启用客房数×天数；预订占用率=启用客房已订间夜/启用库存间夜，四舍五入一位小数。无启用客房返回null，不伪造0%。停用客房未结束预订单独返回inactive_booked_room_nights并提醒核对。每日明细与总数同口径；基础房价为当前启用房型设置范围，不是成交均价或收入。没有新增指标表、历史容量快照或实际入住记录。
