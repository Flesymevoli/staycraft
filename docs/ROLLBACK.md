## 每个模块的固定顺序

1. 从 `TODO.md` 只选择一项，确认允许修改的文件、预期行为和验收场景；先同步必要的 PRD/架构/设计约束。
2. 实现后检查 `git diff`，运行与模块对应的自动测试；涉及页面时还要检查主流程、加载中、空数据、接口错误和移动端布局。失败先修复，不带着失败进入下一项。
3. 测试通过后，用 `git status --short` 核对提交内容，单独提交这一模块。提交信息写明功能和验证结果，例如 `feat: add authenticated property access`。在 `TODO.md` 勾选完成项。
4. 记录提交号与测试命令；下一模块从这个可恢复点继续。每个模块都要能独立说明实际完成的能力，不能把示例状态说成真实发送或执行。

当前后端咨询判断模块的验证命令（在 `backend/` 执行）：

```powershell
python -m unittest discover -s tests -v
```

涉及前端代码的模块至少在 `frontend/` 运行 `npm run lint` 和 `npm run build`；交互变化还要在浏览器验证目标路径与关键状态。新增数据迁移或外部动作时补对应的权限、失败恢复和重复提交测试。

## 如何回滚

- **已提交、尚未共享的单个模块：** 优先保留历史，执行 `git revert <模块提交号>` 生成反向提交，再运行该模块的相关测试。若只是工作区中未提交的实验，先用 `git diff > 临时补丁文件` 保存改动，然后只对明确的文件执行 `git restore --source=<最近通过验证的提交号> -- <文件路径>`。检查路径与差异后再操作。
- **已经共享或部署的模块：** 在 `main` 上 `git revert <模块提交号>`，测试通过后按原部署流程重新发布；不要改写共享历史。若问题来自配置或外部服务，先停止受影响的外部动作，并回滚配置或关闭功能开关。
- **数据库变更：** Git 回滚代码不会还原数据库。迁移必须有前向修复脚本或经过验证的恢复步骤；执行前备份数据并确认恢复点。涉及已写入的客人消息、退款等记录时，不用 `git reset --hard` 或直接删除数据冒充回滚。

回滚后复测受影响用户旅程，确认功能和数据状态一致，再继续下一任务。若一次提交包含多个模块，应先拆分提交，避免回滚时撤掉无关功能。
