# Homestay AI｜界面与交互边界

## 当前云端流程 · 2026-10-22

保留五页布局与纯色背景。客房表单仍同页填写房号与房型，图片上传后随房型保存；保存中锁定重复提交，失败保留输入。旧本机数据只在云端空且检测到旧资料时显示导入入口。

工作台的预订订单区域提供“查看客人预订页”，链接绑定当前民宿。真实直订复用既有客人端视觉，展示云端房型、房量、价格，提交后显示数据库确认结果。独立旧原型保持不变。订单保留不付款说明，正常预订无需人工确认。

首页常驻日程显示日期、房号、客人和预计到店/计划离店；读取失败不显示旧订单冒充成功。清洁为可入住不等于真实入住，预订状态不可读时只显示已清洁/待清洁。工作台和详情区可刷新，返回浏览器窗口也会更新。

## 客人端原型 · 2026-10-22

沿用ink/blue/page与Outfit、白色圆角材质，独立/guest入口。顶部民宿标识，场景图→日期人数→房型→入住须知，底部仅预订/订单/联系三个入口。预订为单独页面，订单详情原位展开，咨询可关联本机订单。场景图标明示意，不当作房间实拍；订单显示待确认及本机演示，不假称真实发送或锁房。手机优先；当前桌面居中预览，完整经营端桌面适配另作下一模块。

版本：v1.0 · 2026-10-15  
基线：`frontend/src/components/` 中的五页原型；产品范围见 [PRD.md](PRD.md)。本文件记录当前选定的视觉方向及开发时必须补齐的状态，不把旧版单文件原型当作设计源。

## 1. 设计原则

以用户认可的首页为视觉锚点：简约、轻透、克制，呈现接近 iOS 的移动端阅读和操作体验。先显示经营者要看的信息与要做的事，减少海报式标题、重复数字和大面积色块。五页共享字体、卡片、按钮和底部导航；颜色用于说明状态与强调操作，而非按功能页重新换一套风格。

手机优先，当前页面内容宽度最多约 430px；更宽视口居中呈现。默认英文，可切换中文。中文文本长度可能更长，组件不得依赖英文单行宽度。原型里的品牌名、照片、日期及业务数字都是示例内容。

字体优先 Outfit，中文回退到 PingFang SC / Microsoft YaHei。页面主标题约 28px，区块标题 20px，任务标题约 18px，正文以 13–14px 为主；首页问候语约 40px。至少保持清楚的标题—说明—操作层级，不靠加大所有文字制造重点。主要点击目标不少于 44×44px，底部导航需留出安全区与页面底部空间。

| 组件 | 规则 |
| --- | --- |
| 页面外壳与底部导航 | 五页一致；图标加文字；当前项有浅蓝胶囊与 `aria-current`，内容不可被浮动导航遮挡。 |
| 标题行 | 左侧清楚命名，右侧可放时间范围、数量或语言切换；不额外添加口号。 |
| 普通卡片 / 列表行 | 同一白色材质和圆角；信息密度按任务调整。消息使用列表行，决策使用可展开卡片，资料使用设置列表。 |
| 主要按钮 / 次级链接 | 蓝色胶囊仅强调下一步或确认；次级动作以文字和箭头表达。危险或不可逆动作不能沿用普通“已完成”反馈。 |
| 指标卡 | 数值、单位、周期、来源同时可见。Analysis 的五项概览并列；只显示一个选中详情，卡片要有“查看详情/正在查看”和选中态。 |
| 日期与图表 | 首页选中日期为深色圆；Explore 日历以浅蓝圆点表示需求强弱，选中日期为深色；图表须标明指标、单位、时间和所选点，不能只靠颜色传达。 |

## 4. 关键交互

- **Home → Work：** 首页待决策项直达对应处理项，处理后首页数量与 Work 记录一致。
- **Work：** AI 回复开关有明确开/关文案；客人列表点开进入对话详情，可返回列表、查看回复依据并补充回复。提前入住与退款先展开事实和方案，再选择处理结果。处理中、待决策、已完成不能混为一栏。
- **Analysis：** 点击指标卡切换下方唯一详情，选中卡有浅蓝状态和文字提示。入住率的 7/28 天切换、图表日期选择及评分分布展开应有可见反馈。底部先给直白总结，再给可点击的决策入口。
- **Explore：** 折线图与日历共同选择日期；点击日历后，日期说明在日历下方展开，避免遮挡。周边线索进入推广卡，文案可编辑后保存；房价比较不触发调价。
- **Mine：** 字段逐项编辑、保存或取消；上传后先展示文件与拟更新项，人工审核前不得静默覆盖民宿事实。

动效只服务于状态变化，常规反馈保持短促。已有实现尊重 `prefers-reduced-motion`，后续新增动画也必须提供减弱运动的表现。键盘焦点要有清晰的蓝色轮廓；焦点与选中状态不能混淆。

## 5. 加载、为空、错误及真实性

这些状态是**正式功能的设计要求**，不代表现有静态演示都已实现。

| 状态 | 视觉与文案要求 |
| --- | --- |
| 加载中 | 在原位置显示骨架或简短进度，保留标题和上下文；标明正在获取消息、分析或生成草稿，不用无限旋转代替结果。 |
| 无数据 | 说明是“暂无消息/预订/评价”还是“尚未接入数据源”，给出下一步；不自动补入虚构业务数据。 |
| 资料不足 | AI 明确指出缺少哪项民宿事实或第三方确认，让经营者补充或接手。 |
| 接口失败 | 保留已输入的文本与已有数据，给出重试和人工处理入口；不得显示“已回复/已退款/已保存”。 |
| 未授权或无权限 | 清楚提示当前账号不能查看或执行什么，并提供返回路径；不暴露客人隐私。 |
| 演示数据 | 持续标注“示例/虚构/未连接平台”，包括图表、市场信号、评价、照片、订单状态和 AI 文案。 |

所有成功提示都要与真实结果对应：保存草稿、向客人发送、退款、发布是四种不同状态。颜色、图标和文字应共同表达状态；不要用同一枚蓝色按钮暗示它们已经全部执行。

## 6. 验收边界

在 320px 左右窄屏与常见手机宽度下无横向溢出，正文不被底部导航覆盖；中英文均可读。键盘可到达全部操作，按钮有名称，图表有文本解释，状态切换可被辅助技术获知。每个业务模块至少检查主流程、加载中、为空和接口失败；视觉差异应回到本文件令牌或明确更新设计决定，不靠页面末尾不断叠加覆盖 CSS。

### Mine 本机回复依据

沿用现有白色圆角卡片、灰色辅助文案与蓝色主按钮。早餐与入住时间在同一卡片维护，只有「确认并保存」成功后显示保存反馈；失败保留输入供重试。空值允许保存为移除依据。入口与 Work 双向链接，标签必须区分本机资料和其他示例字段。

### 房态看板

首页沿用白色圆角卡片与现有字号，按楼层排列紧凑房间按钮，文字配小色点区分状态，不使用整块强色背景。选中房间使用蓝色细边框与轻底色，下方原位展开详情。三种状态均须有可读文本，支持键盘操作与收起；演示清洁反馈不冒充真实客房状态更新。

房态视觉评审补充（2026-10-21）：按最新评审，可入住用绿色、已入住用黑色、待清洁用全局蓝色。房间卡片恢复舒展间距，优先从首页问候区上方留白节省空间；移除日历旁 Demo data 标签。示例说明继续保留在页脚及房态语义标签中。

紧凑布局评审：Explore月历日期行高44px，保留34px圆形状态与下方展开详情；减少行距和上下留白，不缩小日期字号。Analysis五张指标卡图标与名称同行；下排三张减少重复留白，使常用宽度下接近方形，选中保留浅蓝底。指标读取中显示短横占位，失败显示重试，缺客房资料不展示0%经营结论。

房态持久化反馈沿用原详情区域：读取中/空/错误不展示虚假统计，失败可重试；保存中禁用重复操作，成功后再改变房态和统计。卡片底部保留9月17日示例快照提示，不把本机清洁记录包装成OTA更新。
