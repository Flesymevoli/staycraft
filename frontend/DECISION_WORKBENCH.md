# StayCraft 决策工作台：实现与验收

更新：2026-11-04。本说明区分离线夹具、虚构民宿的云端经营数据和真实酒店报价；不是商业效果验证报告。

## 产品结构

`/app` 是自动经营诊断总览；`/app/work` 管理房态、订单、CSV 和运营任务；`/app/analysis` 展示可交互经营指标；`/app/explore` 提供市场报价与周边客源地点；`/app/mine` 维护民宿资料；`/app/promotion` 生成、编辑、保存正式/营销两版文案。原有订单详情、房间详情和历史入口保留。

桌面使用侧栏、宽屏指标区和分析/证据双栏；手机使用四项主导航，资料和推广是辅助入口。公开首页与登录页均支持直接体验既有演示账号，保留普通登录/注册。旧 `/native-*` 原型未修改。

## 架构与工具

浏览器打开总览 → 同源 POST `/api/workspace/agent` → 校验 Auth 与所属民宿 → Supabase 读取初始七日指标及库存 → 模型选择只读工具 → 服务端校验参数、执行并记录结果 → 将观测交回模型 → 继续调查或输出结构化结论 → 校验数字/引用/操作边界 → 保存并展示。

| 工具 | 输入与输出 | 边界 |
| --- | --- | --- |
| `get_metrics` | 起止日期；已订/可售/空余间夜、分摊金额和每日分布 | 最多60天；历史房量未知则不推算历史占用率；金额不是实收 |
| `get_inventory` | 当前启用房量、待清洁总数及房型挂牌价格 | 当前截面，不代表历史或未来现场状态 |
| `get_bookings` | 指定期间重叠订单的日期、房型、状态、金额、来源和入住状态 | 不选取客人姓名、电话；最多读取100条并标记截断；模型上下文仅展示前12条明细 |
| `query_market` | 模型选择未来入住夜；服务端使用所属民宿地址请求 RollingGo `searchHotels` | 一晚、一间房、两成人、最多5家；只读，不接受任意 URL 或外部 property ID |

模型直接返回原生 `tool_calls`，服务端执行后反馈观测，支持多轮继续调查。没有先用固定规则生成候选再让模型排序。规则摘要仅在模型关闭、失败或输出未通过校验时使用，`engine=rules_v1` 明确区别于 `model_v1`。

核心文件：`src/lib/decision-agent.ts`、`decision-agent-types.ts`、`decision-agent-store.ts`、`market-tool.ts`、`model-provider.ts`、`src/app/api/workspace/agent/route.ts`。

## 模型服务与预算

课程网关优先；网络失败、非400的 HTTP 错误、响应未完成，或课程调用预算不足以继续汇总时，使用配置好的 DeepSeek 官方备用服务。同一调查切换后继续使用备用服务，避免反复打主网关。备用密钥仅来自服务端环境/Cloudflare Secret；不返回浏览器，不保存进诊断结果，也不写入 Git。400 和 content_filter 不自动切换，避免绕过供应商内容过滤。

官方模型使用已实测可用的 `deepseek-flash`，关闭 thinking。推广生成复用同一服务选择逻辑。两版推广都只使用现有资料，不保留旧的“虚构民宿可编造设施”豁免；模型不合规时明确使用资料模板。

单次调查最多5轮模型响应、4次新工具执行、2次酒店查询；一次课程失败最多额外尝试一次官方请求。模型每次输出上限900 tokens，单次总时限65秒、单模型请求25秒、酒店请求18秒、数据读取10秒。压缩已知证据与最近工具交换，不重复提交整个原始轨迹。每个提供商的估算预算不超过9500 tokens，课程预算将尽时转官方汇总，不重新调查；这是估算保护，不是精确计费器。

课程 PDF 明确10,000 tokens/分钟/组；该限制也可能受同组其他功能影响，仍可能429。不会紧循环重试：可切备用，最终失败则保留证据并展示数据摘要。

## 状态、历史和隔离

新增增量迁移 `supabase/migrations/20261104000100_decision_agent_runs.sql`，不修改订单、房价或既有业务表。

- 状态为 `running/completed/limited/failed`；保存开始/结束时间、工具步骤、证据、结果、错误码和模型服务标识。
- `GET ?view=history` 读取最近20条；`GET ?id=...` 读取所属民宿的详情。工作台可回看历史。
- 同一民宿/语言只允许一个数据库级 running 任务；进程内也合并重复请求。相同数据指纹的模型结果缓存15分钟，强制刷新保留60秒冷却；规则摘要45秒后允许重试。
- 90秒以上的遗留 running 任务显示超时，下一次开始时标记失败。本版本不提供后台队列或断点续跑。
- 所有接口先验证当前用户与民宿；RLS 再限制所属民宿读写；匿名没有表权限，authenticated 没有删除权限。客户端不能指定其他民宿供工具读取。
- 诊断日志只保留汇总和脱敏订单字段，不记录密钥、客人姓名或电话。原有业务数据不会被建议自动修改。

## 一次真实调查

2026-11-04，本地正式数据流预览使用已有虚构演示账号，调用官方 DeepSeek 与真实 RollingGo。结果 ID：`0f46f1ce-571f-4688-9115-569c4faa8b1f`；`model_v1 / completed / deepseek_official`，持久化历史和详情读取通过。

1. 初始读取11月4–10日：5间启用房，容量35间夜、已订18间夜、空余17间夜，占用51.4%。这些是云端虚构演示经营数据。
2. 模型选择 `get_bookings`，实际读取9条脱敏订单。
3. 模型选择11月8日的 `query_market`，RollingGo 实际返回5家有效人民币报价，供应商起价150–302元。这些是查询时真实外部报价。
4. 服务端反馈观测后，模型综合结束。核心结论为11月8日空房较集中，以及本店挂牌价高于本次周边起价；同时说明房型/早餐/退改未匹配，不能直接推出最优价。
5. 返回结果的每项建议有实际证据 ID；历史可重读；前后订单全量比较未变。模型调查没有改价或发布推广。

这次真实案例验证了工具选择、实际执行、观测反馈和模型结束。离线评测另验证了“先读其他期间指标，再查市场，再输出”的多轮路径。首次数次课程网关调查曾因格式/数字校验或429降级，这些失败记录保留，不能宣称所有调用均成功。

## 能力边界

当前是页面打开时主动发起的有界调查，不是全天后台监控、多Agent运营组织或自动执行平台。当前没有可靠活动新闻搜索；高德地点不能当作确定的近期活动或新增住宿需求。

报价是指定条件的供应商起价，不是同档房型均价、价格趋势或市场需求预测。数字/引用校验是基础防护，不能证明所有自然语言因果或房间级关联都正确；模型可能把聚合清洁数量与未来订单联系过强，应审核原始证据。尚未进行真实经营者效果评测、压力测试或实体iPhone/微信验收。浏览器手机视口通过不等于真机通过。
